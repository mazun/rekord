# コード推定の3段階化と、ピアノロール上での後からの補正(設計)

2026-10-08 / step 1(設計のみ。コードはまだ変えていない)。同日、ユーザーの回答と合成ロジックの試作結果を反映して改訂。

## 0. 要約

- コード推定を**3つの層**に分ける: 即時(遅延 ≈ 0)/ 0.5 秒 / 2 秒。層ごとに独立した推定器で、各層は**追記専用**(自分の出力を後から書き換えない)。
- 「補正」は**表示側の合成**で起こす。層ごとの変化点を、その層が受け持つ区間だけ**つなぎ合わせる**(§4.2)。
  層が遅れて追いつくたびに、ピアノロールのコード帯が即時 → 0.5 秒 → 2 秒の答えへ差し替わる。
- 見た目は**層で変えない**。層の答えが一致している限り何も動かず、**食い違って訂正が入ったときだけ**フェード・スライドする(§4.3)。
- 画面上部のコード表示(コード名・ローマ数字・テンション)は、ライブ中も止めたロール・再生中も**補正後のレーン**(ライブはレーン先頭、それ以外はプレイヘッド位置)を読む。
  新しいコードが現れた瞬間は、レーン先頭が即時層の答えなので、遅延は即時層のまま。0.5 秒層が決め終えて食い違っていたら、表示もレーンと同時に訂正される。
- バックエンドが出すのは「層ごとのコードの変化点 + その層がどこまで決めたか(`decided_s`)」と「鳴っている音の集合」だけ。合成・描画・アニメーション・テンションの計算はフロントエンド。
- 層ごとにコードの数が違っても(即時層のノイズを消す、0.5 秒層が見落としを足す、2 秒層が分割を併合する)、層同士の対応づけは要らない。対応づけは描画時の重なり照合だけで行う(§4.5、試作で確認済み)。
- 層の追加は「`ChordLayer` を実装して登録する」だけにする。step 3 は2層(即時 + 0.5 秒)、step 5 で3層目を足すだけで済む形。

## 1. 用語: 「遅延」は何に対しての遅延か

`covered`(`NoteTranscriber::covered_seconds`)は、ノートのデコードが**確定済みの時刻**。`covered` 以前のノートは(開いているノートも含め)
もう書き換わらない。ピアノロールのプレイヘッドは、ノートの発音がちょうどプレイヘッドに現れるように調整されているので、
ほぼ `covered`(ブロック 0.256 s 以内)の位置にある。

**層の遅延 D とは「時刻 τ のコードを、`covered` が τ + D に達してから決める」こと。** `D = 0` の即時層は、ノートが画面に出た瞬間のコード。
音声そのものからの遅れ(約 0.5 s)はノート転写の構造的な遅れで、全層に共通。ここは変えられない。

`decided_s` = その層が「ここまでは決め終えた」と宣言する時刻。ほぼ `covered - D`。

| 層 | 名前(コード上) | D | `decided_s` | 役割 |
|---|---|---|---|---|
| L0 | `instant` | ≈ 0 | `covered` | 新しいコードが現れた瞬間の暫定コード(レーン先頭・上部表示に最初に出る) |
| L1 | `settled` | ≈ 0.5 s | `covered - 0.55`(現行ロジック) | 窓・ホールドで安定させた名前 |
| L2 | `confirmed` | 2 s | `covered - 2` | 先読み付きの平滑化で確定 |

現行の `ChordStabilizer` はすでに L1 に当たる。`CHORD_MIN_HOLD_S`(0.25)で保留し、開始を `CHORD_BACKDATE_S`(0.3)戻すので、
実効の遅延は 0.25 + 0.3 = 0.55 s。つまり**今のコード表示が「ユーザーが体感している遅さ」そのもの**で、L0 を新設して新しいコードが現れた瞬間の表示をそちらに移し、後から L1・L2 が補正する、というのが全体の構図。

BeatLines の `predicted / provisional / committed` と同じ関係(即時 / 暫定 / 確定)になる。

## 2. 全体像

```
time ->        c-2.0         c-0.55          c  (= covered ≈ playhead)
                 |             |             |
confirmed   =====]             .             .      L2: c-2 まで決定
settled     ===============]   .             .      L1: c-0.55 まで決定
instant     ============================]           L0: c まで決定
lane        [ L2 の変化 ..][ L1 の変化 ][ L0 の変化 ]  ピアノロールに出る帯(受け持ちの区間をつなぐ)
```

ブロックが進むたびに継ぎ目が右へずれ、各層の受け持ちが広がっていく。層が一致していれば帯は何も変わらず、食い違っていた分だけ
帯の境界とコード名がアニメーションしながら差し替わる(見た目は層で変えない)。

```
rekord_core                                    rekord-piano-roll (frontend)
 NoteTranscriber ─ note_events ─┐
 KeyEstimator ─ current key ────┤
 BeatTracker  ─ beat_grid ──────┤
                                v
                          ChordEngine ──── ChordLayer event ───> Recording (層ごとのログ)
                           ├ InstantLayer      (層ごと、ブロックごと)   ├ stateAt(t) = レーンの t(ライブは先頭)
                           ├ SettledLayer                              └ ChordLane(つなぎ合わせ) ─ 帯 ─> PianoRoll
                           └ ConfirmedLayer  (step 4/5)
                          (TensionsChanged は廃止: 鳴っている音の集合 ActiveNotes を流し、テンションはフロントエンドで計算)
```

## 3. バックエンド

### 3.1 層とエンジン(`rust/core/src/chord_layers/`、現在 `pipeline.rs` にある分を移す)

```rust
pub enum ChordLayerId { Instant, Settled, Confirmed }   // serde: "instant" | "settled" | "confirmed"

/// 層が「この時刻からこのコード」と決めた変化点。ラベル付けは engine が行う(層は ChordAt のまま)。
pub struct LayerChange { pub t: f32, pub chord: ChordAt }

pub struct StepCtx<'a> {
    pub notes: &'a [NoteEvent],        // note_events(): 直近 3.3 s
    pub key: Option<KeyEstimate>,      // その時点の現在キー
    pub beat_grid: Option<BeatGrid>,
}

pub trait ChordLayer {
    /// チェックポイント t(= いまの covered 以下で、時刻順)ごとに呼ばれる。
    /// 新しく決めた変化を out に積み、どこまで決め終えたかを返す。
    fn step(&mut self, t: f32, ctx: &StepCtx, out: &mut Vec<LayerChange>) -> f32; // -> decided_s
    /// 入力の終わり: 保留中を全部決める。
    fn finish(&mut self, covered: f32, out: &mut Vec<LayerChange>);
}
```

`ChordEngine::advance(note_events, prev_covered, covered, …)` が現行の `report_new_chords` の置き換え。

1. チェックポイント列は現行のまま(ノート開始 + 0.05 s グリッド + `covered`)。
2. チェックポイントごとにキー推定を先に更新(現行どおり。`KeyChange` もそのまま出す)。
3. 全層を `step`。あわせて、チェックポイントで鳴っている音(ボーカルを含む全パート)のピッチクラス集合を記録する。
4. ブロックの終わりに、層ごとに `ChordLayer` イベントを1つと、集合が変わっていれば `ActiveNotes` イベントを1つ出す(`ChordLayer` は変化なしでも `decided_s` が進んだら出す)。

層同士は互いの出力を見ない。同じノート列から別々に推定する。理由: 層ごとに単体でオフラインに評価でき(現行の `chord_replay` と harmonica-repro の評価をそのまま使える)、
3層目に別方式(Viterbi など)を入れても他の層が壊れない。

共通部品は `match_chroma` のスコア表(12 ルート × 24 テンプレート)。これを返す関数を `chord_templates.rs` に出しておけば、
L2 は「チェックポイントごとのスコア」を自分で溜めて平滑化できる(ノートは 3.3 s しか残らないので L2 はノートを読み直さない)。

### 3.2 イベント

`ChordChange` と `ChordRelabel` を次の1種類に置き換える。

```rust
PipelineEvent::ChordLayer {
    layer: ChordLayerId,
    /// この層が新しく決めた変化点。時刻順。t から次の変化点(または次のイベント)までそのコード。
    changes: Vec<LayerChord>,         // { t, label, roman_numeral, root_pc, quality }
    /// この層は decided_s までを決め終えた。changes の t は全部 decided_s 以下。
    decided_s: f32,
}
```

- `TensionsChanged` は廃止し、代わりに `ActiveNotes { changes: [{ t, pcs }] }`(`pcs` は 12 ビットのピッチクラス集合、変わったときだけ)を流す。理由は §3.4。
- `Started` に `chord_vocabulary`(テンプレートごとの `quality` と構成音の間隔、テンション名とルートからの半音数の表)を載せる。
  フロントエンドはこの表でテンションを計算する。表の出どころは Rust の `CHORD_TEMPLATES` / `TENSION_NAMES` の1か所のまま。
- `KeyChange` / `BeatLines` / ノート系は変更なし。
- 頻度はブロックごと(0.256 s)× 層数 = 毎秒十数個。`NoteConfirmed` より桁違いに少ない。層ごとに別イベントにしておくのは、
  重い層(step 4)を別スレッドに出したくなったときに切り出しやすいから。
- 同じ `t` の変化点が来たら**置換**(upsert)。スペル設定(♯/♭/Auto)が変わったとき、`ChordRelabel` の代わりに各層の開いている最後のコードを同じ `t` で再送する
  (過去のコードは旧スペルのまま、という現行の挙動と同じ)。

### 3.3 不変条件(エンジンが保証し、フロントエンドは信頼する)

1. 層ごとに `decided_s` は単調非減少。
2. 層ごとに変化点の `t` は単調非減少で、**直前に報告した `decided_s` 以上、今回の `decided_s` 以下**。
   (ビートスナップや戻し補正で `t` がはみ出すときはエンジンが丸める。これで「層が一度決めたと言った区間は二度と変わらない」が成り立ち、合成が安全になる。)
3. 区間に何も鳴っていなければ `ChordAt::Silence` の変化点(= `(silence)`)を出す。「変化点なし」は「同じコードが続く」の意味。
4. セッション開始(`Started`)ですべて空に戻る。入力終了時は全層に `finish` を呼び、`decided_s` を終端に揃える(止まったロールは全部「確定」表示になる)。

### 3.4 キー・スペル・ビートスナップ・テンション

- **キー**: 推定器は今までどおり最新のチェックポイントで1回だけ進め、各層はその「現在のキー」でラベル付けする。
  遅い層が過去の時刻を決めるときも、決めた時点のキーを使う(より情報が多い)。層間でスペルが食い違うことはあるが、遅い層が勝つ区間は遅い層のスペルになる。
- **ビートスナップ**: 即時層はしない(速さが目的。数十 ms のずれは L1 が直す)。L1・L2 は今までどおりコミット時にスナップ。
  スナップで境界が数十 ms 動くのは、補正の一部としてアニメーションで吸収される想定。
- **テンション**: 層の出力に含めない。`ActiveNotes`(鳴っている音の集合。ボーカルを含む。現行の `TensionsChanged` が使っていたものと同じ)と、**画面に出ているコード**(レーンの `root_pc` / `quality`)から、フロントエンドが `extra_tensions` と同じ計算で出す。
  こうすると、ライブ先頭でも再生中でも、補正で表示中のコードが変わったときでも、テンションは必ず表示中のコードに対する値になる
  (層ごとに計算すると、補正後が C なのにテンションは補正前の Am に対する値、という食い違いが出る)。現行の「表示中のコードに対して判定する」意味は変わらない。
- **ローマ数字**: コードの変化点ごとに付く(層ごとにその時点のキーで)。

## 4. フロントエンド

### 4.1 `Recording`(`recording.ts`)

- `chords: Timeline<…>` を層ごとの3本(コード・ローマ数字・`root_pc` / `quality`)+ `decidedS` に置き換える。`Timeline` に「同じ t は置換」を足す。
- 鳴っている音の集合 `ActiveNotes` を `Timeline<number>` に溜める。
- `stateAt(t)` のコード・ローマ数字は `ChordLane.at(t)`(補正後。`t = Infinity` はレーン先頭)、テンションは `tensionsFor(ActiveNotes の t 時点, そのコード)`。キーと BPM は今のまま。
- 履歴は今までどおり `HISTORY_S` で刈る。

### 4.2 `ChordLane`: 合成は「状態の切り替え」ではなく「変化のつなぎ合わせ」(新規、`chordlane.ts`。Svelte にも Pixi にも依存しない)

```ts
interface ResolvedSegment { startS: number; endS: number | null; label: string; roman: string | null; layer: 0 | 1 | 2 }
class ChordLane {
  apply(ev): void                       // ChordLayer イベントを取り込む
  takeUpdate(): { fromS: number; segments: ResolvedSegment[] } | null   // 前回から変わった範囲だけ返す
  at(t: number): LayerReading | undefined   // 補正後の読み取り(コード・ローマ数字・テンション)
}
```

**規則**: 各層の変化点のうち、**その層だけが受け持つ区間**のものを採って時刻順に並べる。

| 層 | 採る変化点 |
|---|---|
| 2 秒層 | `t ≤ D2`(2 秒層の `decided_s`) |
| 0.5 秒層 | `D2 < t ≤ D1` |
| 即時層 | `D1 < t`(先頭まで) |

コードは、この並びを順に適用して得る。継ぎ目では**上の層のコードが、下の層が次の変化を報告するまで続く**(下の層の「継ぎ目時点の状態」は使わない)。
隣り合う区間が同じコード名なら、層をまたいでも1つの帯に結合する(`layer` は構成要素のうち最も浅い層。デバッグ表示用で、描画には使わない)。

最初に考えた規則は「時刻 t の答えは、t を決め終えた最も遅い層の、t で有効なコード」(状態の切り替え)だったが、これは**だめだった**。
層が同じコードを出していても、変わる位置が層で違うだけ(即時層は 0.15 s 遅れて F に変わり、0.5 秒層は 0.03 s)で、継ぎ目に F → Am → F の 10〜140 ms の切れ端が出て、
そのたびにフェードする。試作(§4.5)で、全層が一致するシナリオに**フェードアウト 6 回 + フェードイン 3 回**が出た。つなぎ合わせなら 0 回。

この規則の性質:

- 層が一致している間は何も起きない。食い違いは、下の層が先に出した答えを上の層が決め終えた瞬間に**一度だけ**訂正され、その後は動かない。
- 食い違いが続く場合(0.5 秒層は Am、即時層は C と言い続ける)でも、レーンにも上部表示にも訂正後の Am が出続ける。上部表示とレーン先頭が食い違うことはない。
- 層同士の対応づけ(「0.5 秒層のこの変化は即時層のあの変化」)は要らない。層の変化点の**数が違っても**、並べて適用するだけで済む。

`takeUpdate` は、イベントで変わりうる最も早い時刻 `fromS`(その層の旧 `decided_s` と新変化点の最小)以降だけを返す。5 分間の帯をブロックごとに作り直さない。

### 4.3 ピアノロールの描画(`pianoroll.ts`): 変わるときだけ動く

- **層による見た目の違いはつけない。** 即時でも確定でも同じ見た目。一致している間は何も動かない。
- `addChordChange` / `relabelCurrentChord` をやめ、`setChordSegments(fromS, segments)` に置き換える。`setBeatLines` と同じ作りで、
  `fromS` 以降の既存スプライトと新しい区間を**同じラベルで重なりが最大のもの同士**で1対1に貸し借りする(貪欲法。同ラベルの順序つき区間では交差しない)。
  - **貸し借りできた**: 境界位置を `CHORD_ANIM_TAU_S`(初期値 0.15 s、BeatLines と同じ)でスライドするだけ。ラベルは同じなのでフェードはしない。ビートスナップによる数十 ms の補正はこれ。
  - **新しい側が余る**: フェードイン(訂正で増えた帯)。
  - **古い側が余る**: フェードアウトして破棄(訂正で消えた帯)。フェードアウト中のものは新しい帯の下に描く。
  - **ラベルが変わる**(Am → C): 同じ区間で古いほうがフェードアウトし、新しいほうがフェードインするので、結果としてクロスフェードになる。
  - **普通の進行**(先頭に新しいコードが足される)は訂正ではないので、今までどおり即座に出す。判別は「新しい区間の開始が、これまで描いていた先頭より後ろ」。
  - 別の同名の帯に飲み込まれて消える帯(ノイズに分断されたコードの後半)は、文字が重なって見える時間を短くするため、短い時間(約 0.08 s)でフェードアウトさせる。
- 帯の交互の色(`CHORD_BAND_COLOR_A/B`)は、`fromS` 以降を作り直すときに直前の帯から数え直し、色が変わるものは `CHORD_ANIM_TAU_S` で色を移す。それ以前は動かさない。
- 描画するのはオンスクリーンだけ(今と同じ)。5 分間の履歴スプライトは区間単位の `visible` 切り替えのまま。
- 層を色で見られるデバッグ表示(既定オフ)を足してもよい。必要になったら。

### 4.4 上部表示と再生

- ライブ: `showDisplay(recording.stateAt(Infinity))` がレーン先頭を読む。新しいコードが現れた瞬間は即時層の答え、0.5 秒層が決め終えたら訂正後の答え。
  `ChordDisplay.svelte` / `TensionGrid.svelte` は表示だけなので変更不要。テンションはノートのイベントでも変わるので、`showDisplay` はノートのイベントでも(フレームに1回にまとめて)呼ぶ。
- 止めたロール・再生中: `stateAt(t)` がプレイヘッドの t で同じ計算をする。コード名・ローマ数字・テンションが全部、帯に出ているものと一致する。

### 4.5 層ごとにコードの数が違うとき(試作での確認)

層は互いに独立なので、変化点の数はいくらでも違ってよい。§4.2 の合成と §4.3 の貸し借りだけで、増減・分割・併合が扱えることを、
合成・照合ロジックだけの Node 試作で確認した(ブロック 0.256 s ずつ進め、各層が自分の遅延 {0, 0.55, 2.0 s} で決めたものを順に与える。真のコード進行は C 2 s / Am 2 s / F 2 s / G 2 s / C)。
表の数字は 11 秒間に起きた**帯のフェードアウト / フェードイン**の数(先頭に新しいコードが現れる普通の進行は数えない)。1回の訂正で2本の帯が動くことがある。

| # | シナリオ | 見え方 | 状態切り替え | つなぎ合わせ |
|---|---|---|---|---|
| 0 | 全層が同じコード。境界の位置だけ違う(即時 +0.15 s、0.5 秒 +0.03 s) | 何も起きない(境界のスライドだけ) | 6 / 3 | **0 / 0** |
| 1 | 即時層にだけ短い誤り(Dm が 0.12 s)(減) | 誤りの帯がフェードアウトし、前後の同じコードが1本につながる | 8 / 3 | 2 / 0 |
| 2 | 0.5 秒層が即時層の見落としを足す(Em)(増) | Em と、分割された後半の Am がフェードイン | 6 / 4 | 0 / 2 |
| 3 | 即時層が新しいコードの最初の 0.25 s を誤る(ラベル同じ・位置違い) | 境界がスライドするだけ | 4 / 2 | **0 / 0** |
| 4 | 0.5 秒層が F を Dm の誤りで分割し、2 秒層が併合(減) | 分割は 0.5 秒層が決めた後に見え、2 秒後に消える | 8 / 4 | 2 / 2 |
| 5 | 0.5 秒層が F を 2 s 間 Dm と誤り、2 秒層が訂正 | Dm が出て、2 秒後に F に差し替わる | 7 / 5 | 2 / 2 |
| 6 | 即時層が約 0.7 s ごとにノイズ(X) | ノイズは先頭に出て、0.55 s 後に消える | 31 / 3 | 27 / 0 |
| 7 | 即時層がコード全体を誤る(Am を C) | 0.55 s 後に一度だけ差し替わり、その後は動かない | 7 / 4 | 0 / 1 |

確認できたこと:

- 層が一致するなら何も動かない(0, 3)。動くのは本当に食い違った分だけ。
- つなぎ合わせでは、継ぎ目由来の切れ端は出ない。レーンに現れる最短の帯は、シナリオで意図的に入れたノイズ(50 ms)だけ。
- 即時層のノイズ(6)は、先頭には出る(即時層の性質)。0.5 秒層が決め終えると消える。ノイズが続くほどフェードが多く見えるので、
  **即時層のチューニング(step 2)は「ちらつき」を評価項目に入れて抑える**(§5-4)。

試作はスクラッチパッドにあり、リポジトリには入れていない。step 3 で上の表のシナリオを `ChordLane` の自動テストにする(表がそのまま仕様)。

## 5. CLI・評価ツール

- `rekord_engine`(CLI)は `ChordLayer` イベントを層ごとに印字: 既定は `settled` だけを今と同じ書式
  (`  t= 12.34s  chord: C  (I)`)で出す。harmonica-repro の変換・評価スクリプト(`rekord_labels.py`)と過去の数値がそのまま再現できる。
  `--chord-layer instant|settled|confirmed|all` で切り替え。
- `chord_replay` は層ごとに `NNN.l0.txt / .l1.txt / .l2.txt` を書く。
- harmonica-repro 側に足す評価(step 2 の中身):
  1. 層ごとの精度(既存の majmin / majmin_inv / sevenths / tetrads)。
  2. **合成後の帯**の精度(= ロールに最終的に残るもの)。
  3. **表示遅延**: 正解のコード境界から、その層が正解のコードを初めて出すまでの時間(中央値 / p90)。
  4. **ちらつき**: 1分あたりの変化点数(正解の何倍か)。
  5. **補正の効果**: 即時層の誤りのうち L1 / L2 で直った割合、逆に正しかったのが悪化した割合。
  6. **レーンで見えるフェードの頻度**: 即時層と0.5 秒層の読み取りが食い違う区間の割合と回数(1分あたり)。「ほとんどの場合で変わらない」を数字で確かめる指標で、
     食い違いのうち「ラベル違い(フェードする)」と「位置だけ違い(スライドだけ)」を分けて数える。
  ここまで測れてはじめて「即時層はどこまで粗くてよいか」を決められる。

## 8. 決定済みのこと / 採らなかった案

決定済み(ユーザー確認、2026-10-08):

1. 段階は 即時 / **0.5 秒(現行ロジックの実効遅延 0.55 s)** / 2 秒。step 3 の「0.25 秒」は誤記。
2. 上部表示は**補正後のレーン**に合わせる(ライブはレーン先頭、止めたロール・再生中はプレイヘッド位置。§4.4)。ライブ中に即時層と0.5 秒層が食い違い続けても、上部とレーンは一致する。
3. 層による見た目の違いはつけず、**層の答えが変わるときだけフェード / スライド**する(§4.3)。

step 3 で確認すること(設計で決まっていないもの):

- 描画のパラメータ(`CHORD_ANIM_TAU_S`、ノイズ帯を消すフェードの長さ)はライブで調整する。
- `ActiveNotes` はテンションの集合ではなく音の集合が変わるたびに出るので、`TensionsChanged` より多い(最大でチェックポイントごと = 毎秒 20)。ブロックごとの1イベントにまとめて送るので IPC の負荷は小さいはずだが、多すぎれば測って間引く。

採らなかった案:

- **ID 付きの訂正イベント(`ChordRevise { id, … }`)で1本のレーンを直す**: ID 管理・分割・結合の状態がバックエンドとフロントエンドの両方に要る。層ごとの追記専用なら、各層は評価ツールで単体評価でき、順序や取りこぼしにも強い。
- **BeatLines 方式で全層のスナップショットを毎回送る**: 5 分レーンでも小さいが、確定済みの区間まで毎回送る意味がない。追記 + `decided_s` で足りる。
- **バックエンドで合成してから送る**: 上部表示が即時層を別に必要とすること、再生時に層ごとのログが要ること、描画側で層の食い違いを貸し借りで扱うことから、合成はフロントエンドに置く。
- **「t を決め終えた最も遅い層の、t で有効なコード」という状態の切り替えによる合成**: 層の継ぎ目に切れ端が出て、一致しているのにフェードする(§4.2、試作で確認)。変化点のつなぎ合わせに変えた。

### 9.2 評価の方法

RWC-Pop 100 曲(Mix 条件、ファイル入力。ビート補正なし)。ノート列は baseline の `raw/` を使い回し、コード判定だけを再生する(1 設定 約 30 秒)。
奇数番号の曲で調整し、偶数番号の曲で確かめた。指標は `layer_metrics.py` の docstring にある。

- **pos** = コードを開始時刻 `t` に置いたときの mir_eval の精度(従来の評価と同じ)。
- **live** = コードを発表時刻 `emit` に置いたときの精度(= その時刻に画面に出ていたものを、その時刻の正解と比べる。遅れも精度に入る)。
- **遅延** = 正解のコードが(majmin で)切り替わってから、正しいコードが 0.1 秒以上出るまでの時間(ノート転写の遅れに上乗せされる分)。
- **fades/min** = レーンで見えるフェードの数の見積もり(即時層の区間のうち、0.5 秒層に同じラベルで重なる区間がないものの数。境界のずれだけのものは数えない)。
- **fix / regress** = 即時層が間違いで 0.5 秒層が正解になった時間 / その逆の時間の割合(majmin)。

### 9.4 何が効いたか(スイープ 約 120 設定、調整用の奇数曲)

| つまみ | 結果 |
|---|---|
| 保留 `h`(新しいコードが何秒先頭にいてから切り替えるか) | **最も効く**。初期案(窓 0.2 s)の 200 フェード/分 は、保留 0.1 s・スラッシュなしで 23、0.15 s で 16 になる(`m=0.2`)。代わりに保留 0.05 s ごとに遅延が約 0.05 s 増える |
| 余白 `m`(今のコードのスコアに足す有利さ) | **遅延を増やさずにフェードを減らせる**。同じ `h` で `m` 0.2 → 0.4 にすると fades 16 → 12 /分、遅延は同じ。0.8 以上は粘りすぎて精度が落ちる(majmin .757、出ずに終わる割合 20%) |
| スラッシュのベース音 `c=1` | **フェードの約 3 分の 1 を消す**(C と C/E の違い)。pos majmin も上がる(.750 → .773)。majmin_inv も settled を上回る(.737 対 .702) |
| 三和音のみ `c=2` | 採らない。フェードが増える(0.5 秒層が 7th / 9th を付けるたびに食い違う: 16 → 26 /分) |
| 窓の形 | 箱型 0.15 s より、0.4 s・減衰 0.1 s のほうが同じ遅延・ちらつきで精度が +0.01(majmin .772 → .782) |
| 直前の変化の直後だけ保留を長くする(`r`, `rh`) | 単純な保留と同等以下。採らない(step 3 でパラメータごと削除) |
| 巻き戻し `b` | 0.05 → 0.1 で pos majmin +.002。0 は -.014。それ以上は変わらない |
| 無音の判定時間 `sil` | 0.1〜0.5 s で差はほぼない |

### 9.5 残るフェードの内訳(既定、毎分 15 回)

ルートが違う 約 7 回(0.25 s 以上続くもの 6 回)、スラッシュ違い 約 4 回(0.5 秒層がスラッシュを付けたとき)、
同じ三和音で品質違い(7th / 9th など) 約 2.5 回、その他。つまり 3 分の 1 強は「後の層が情報を足す」精緻化で、本当の誤り訂正はルート違いの約 7 回。

### 9.6 分かったこと(step 3 以降に効く)

- **現行の 0.5 秒層は、即時層より正確とは言えなくなった。** 開始時刻を正解に合わせた精度(pos)では、即時層(既定)が majmin .793 / sevenths .655 / tetrads .592 で、settled の .769 / .642 / .587 を上回る。
  補正の効果(majmin、時間の割合)は fix 4.6% に対して **regress 7.1%**(即時層が合っていたのに 0.5 秒層が間違いに直した時間のほうが長い)。
  補正が補正として働くには、0.5 秒層も改善が要る。同じ道具(余白・減衰窓)で 0.5 秒層を調整して `fix` が `regress` を上回るようにするのを、step 3 の作業に含めることを提案する(現行ロジックの 1:1 移植を先に行って一致確認をしたうえで)。
- 即時層の「出ずに終わる」割合(13%。settled は 17%)は、ノート転写が拾えないか、全く違うコードを出している区間。原因別には調べていない。
- 評価の限界: RWC のラベルは add9 / 9 / 11 / sus2 / power chord をほとんど含まず、装飾的なコードは常に外れ扱い(CLAUDE.md の注意と同じ)。遅延は人が付けた境界(±0.1〜0.2 s)に対する値。
  レーンの見え方(フェードの感触)は、step 3 でライブアプリを見て判断する。

### 10.2 試作から変えたこと(実装中に見つかった欠陥)

1. **継ぎ目の猶予(`HANDOVER_GRACE_S` = 0.25 s)**: 遅い層は保留中の挑戦者の最も早い開始時刻まで「決定済み」と宣言するが、その変化はまだ報告していない。

   遅い層の最後の変化より後の、継ぎ目の直前の速い層の変化は残す。遅い層が報告したらそちらに譲る。
2. **更新は、変化した時刻にあった帯の「ひとつ前」から返す**: 現在進行中の帯(終わりが未定)は、次のコードが始まると終わりが決まる。それを含めないと、前の帯が消えたものと扱われた。
3. 帯が「ただ先頭に増えた」のか「補正で増えた」のかは、即時層の帯で先頭の近くかどうかで決める(0.5 秒層が足した帯は、先頭に近くてもフェードインする)。

### 10.3 0.5 秒層の改善(ユーザー指示: step 3 に含める)

即時層が 0.5 秒層より高精度という step 2 の発見を受けて、0.5 秒層を余白・減衰窓・窓長・保留・巻き戻しで掃引した(約 35 設定、奇数曲で調整・偶数曲で確認)。
減衰窓と長い窓は悪化(減衰 0.3 s: 遅延は縮むが majmin -.01、窓 0.8 s + 減衰なし: 遅延 0.72 s で -.03)。保留と巻き戻しは今の値(0.25 s / 0.3 s)が平坦な最適付近。

## 11. ライブ確認後の調整: maj/min の取り違えとキー推定、即時層の既定(2026-10-09)

ユーザーがライブで確認した結果(step 3 の確認の途中):

1. 即時層は `c=0,h=0.05` でよい(スラッシュあり、保留 0.05 s)。
2. 0.5 秒層で「体感で maj/min の区別が弱くなった」。余白 0.2 を入れたせいか。サビで転調する曲(手持ちの CD)を例に、キー推定が追いつかず、明らかに長調の音なのにキーにつられて短調になる。キーを正確に拾う方向と、3度が鳴っているときはキーの効きを弱くする方向の両方を検討してほしい。

### 11.1 余白 0.2 は原因ではない

RWC-Pop 100 曲で、正解が長3度か短3度のコードで根音が合っている時間のうち、推定の3度が**逆**(長と短が反対)だった割合
(`harmonica-repro/tools/chord_eval/third_confusion.py`):

| 設定 | 逆になった割合 |
|---|---|
| settled、余白なし(旧) | 3.70% |
| settled、余白 0.2(現行) | **3.28%** |
| instant(旧既定) | 3.62% |
| instant(`c=0,h=0.05`) | 3.63% |

曲ごとでは、余白で 2 秒以上悪くなったのが 6 曲、良くなったのが 15 曲(最悪でも +3.3 秒、曲は約 4 分)。弱くなったのではなく、わずかに良くなっている。

### 11.2 cdex:2c6693d2bd4f で起きていること

ユーザーの挙げた調のタイムライン(C → 1:00 から A → 1:36 から C → 2:33 から A → 3:46 から C。A の借用部分は C でもよい)を正解にして、
0.5 秒層で「調のダイアトニックと食い違う長短(例: A major の中の Dm / Em)」の時間を数えた(`scratchpad` の `song_eval.py`。曲全体 230 秒のうち):

| 条件 | 食い違う時間 |
|---|---|
| 現行のキー推定 | 14.6 秒 |
| 正解の調を与える(上限) | **8.8 秒** |
| 調を使わない | 10.5 秒。ただし `5`(3度なし)が 43 秒に増える |

- 調に引きずられた誤りは 5.8 秒分(サビ頭の Am、Dm、Em など)。残りの 8.8 秒は調とは別(C の中の F が Fm になる所など。`G♯` の音が 8〜14% 鳴っている)。
- 原因の連鎖: 伴奏(ギターの 5度、ペダル)に**3度が鳴らない** → 名前が `5`(ルート + 5度)になる → `chord_templates.rs` の規則(3度が 12% 未満の `5` は調のダイアトニックの三和音にする)でキーの音階の質になる → キー推定が転調に **7〜15 秒遅れる** → 古い調(C)の音階で Dm / Em になる。
  例: 62.5 s の窓は伴奏が A と B だけで C♯ は歌にしかない。66〜67 s の D の和音には F♯ が伴奏にも歌にも無い(C♯ = 長7度は 66.5 s まで鳴る)。3度は和音が始まって約 1 秒後に出て、そこで Dm → Dadd9 と直る。
- キーの遅れは、サビ頭の 60〜66 s の音が A major より **A minor(= C major と同じ音階)** にいちばん合うことにも由来する。長3度がまだ鳴っていないので、短調のプロファイルが勝つ。

### 11.3 方向 B: 3度が鳴っているときにキーの効きを弱くする → 効かなかった

試したこと(`ThirdRule`。実験の後で削除した): (a) 伴奏の3度がもっと低い割合(3〜8%)でも、長短の片方だけが鳴っていればそれで決める。(b) 歌の3度を足す。(c) 長7度が鳴っていれば長3度の証拠にする(短三和音に長7度が付くことはまれ)。
結果: RWC majmin .778 → .779(+.001)、cdex:2c6693d2bd4f の食い違い 14.6 → 13.9 秒。**そもそも音符の中に3度が無い**ので、証拠で上書きできる和音がほとんど無い。方向 B は採らない。

### 11.4 方向 A: キーを正確に、速く拾う

評価の道具(`harmonica-repro/tools/chord_eval/key_eval.py`): RWC-Pop 100 曲の正解コードから、先読みあり(前後 8 秒)で基準キーを作り(相対長調の主音 12 通り。Viterbi で区間化)、推定キーとの一致・切り替え回数・追いつくまでの遅れを測る。
基準が正解コードのラベルから来るので、音符から推定する Re:Kord とは独立。cdex:2c6693d2bd4f は別にユーザーのタイムラインで測る。

### 11.6 残っていること

- サビの**最初の和音**(62.3 s の Am 0.8 秒)は、その時点の音にもキーにも証拠が無い。3度が鳴る約 1 秒後に直る。step 4 の 2 秒層(前後の文脈)で直せるはずの典型例。
- 和音が始まって 3度が鳴るまでの約 1 秒は、キーが合っていても `5` のまま(キーが合えば正しい長短になる)。

- キー表示の切り替えが基準より多い(2.8 回/分に対し 1.0)。転調の瞬間を拾う速さとのトレードオフ。表示のちらつきが気になるなら `cusum_s` を上げる(`REKORD_KEY_TUNE="l=2,df=0.25"` で 1.6 回/分、一致 .745、遅れ 7.4 s。ただし cdex:2c6693d2bd4f の食い違いの改善は消えて 14.6 秒に戻る)。

## 12. step 4 の結果: 2 秒層(確定層)の実装と評価(2026-10-09)

`chord_replay` の `layer=confirmed` と `ChordEngine::with_confirmed` で動く(step 5 で `standard()` にも登録した。§13)。

### 12.1 作ったもの

`rust/core/src/chord_layers/confirmed.rs`: **`ConfirmedLayer`**(固定遅れ Viterbi)。

- 0.1 秒ごとの時刻(ビン)に、その前後 0.4 秒(うち 30% が後ろ側)の音から、全テンプレート × 12 根音のスコアを付ける。
  数式は他の層の `match_chroma` と同じ(`chord_templates.rs` に `score_templates` として切り出した。既存の 2 層の出力は 100 曲で変更前と完全に一致)。
- 状態は (根音, 品質, ベース音) と無音。状態を変えるのに別のコードなら **2.5**、同じコードでベースだけなら **3.0** のコストを払う。
  ベース音の状態には、ベースパートの割合 × 0.2 の加点、根音以外のベースには 0.05 の減点を付ける。
- ビン n が決まったら、その時点の最良の経路をたどって 17 ビン前(約 1.7 秒前。`delay_s` = 2.0 から窓の先読みを引いた分)の状態を確定し、変わっていれば変化点として出す。
  確定済みは書き換えない。`finish` は直前のステップで取っておいた、まだ窓が埋まっていないビンのスコアを足して、残りを全部決める(`finish` はノートを受け取らないため)。
- 3度の無い和音(`5`)の補完は他の層と同じ考え方(その音階の三和音)だが、**ビンのスコアに足すだけで、上限を付けた**(`key_lift` = 0.03: キーは、長短どちらも3度が鳴っていないときの同点の決め手にしかならない)。
  さらに、この曲でその根音の和音が決まったときに実際に鳴っていた3度(長 / 短)を覚えておき(時定数 60 秒)、1 秒分以上の記憶があり 7 割以上が同じなら、キーより先にそれを使う。
- 層の契約(`decided_s` は単調、変化点は直前の `decided_s` 以上・今回の `decided_s` 以下)はテストで確認。1 秒の音声あたり約 0.4 ms(5 曲 約 20 分の再生が 0.73 s → 1.21 s)。

## 14. 短い aug(ブラックアダー・コード)を出す(2026-10-10)

再生中の曲で、Gb の終わり 1.5 拍(ベース C、音は Gb・Bb・D)が `Gbaug/C` ではなく `Gb` のままだった。ライブログ(`rekord_engine --live` の標準出力をそのまま `chord_replay` の入力にできる)で調べた結果:

- 原因はテンプレートの事前値 `aug` = 0.5(窓内の比 .90 の aug が .76 の Gb に 0.03 対 0.11 で負けていた)。ベースの C が外側音として減点される分は小さい(C の比は約 10%)。
- aug は Gb・Bb・D のどれを根音にしても同じ音の集合なので、同点だと根音の若い順(D)になる。ブラックアダー・コードは根音の**全音上**をベースに置くのが通例なので、`aug` のときだけ、ベースが根音の全音上にある根音に 0.05 × ベースの比を足して同点を解く(`AUG_WHOLE_TONE_BASS_WEIGHT`)。ベース C なら B♭aug/C。
- 事前値は `AUG_PRIOR` = 0.2 に下げた。0.3 では出ず、0.2 と 0.1 で confirmed 層が B の前の約 0.7 s を B♭aug/C にする(33.25〜33.95 s)。

RWC-Pop 100 曲(pos):

| aug の事前値 | instant majmin / tetrads | settled | confirmed |
|---|---|---|---|
| 0.5(旧) | .791 / .586 | .783 / .601 | .824 / .633 |
| 0.2(採用) | .790 / .587 | .782 / .602 | .823 / .634 |
| 0.1 | .789 / .587 | .782 / .602 | .822 / .634 |

根音の同点解消だけでは RWC の出力は 1 曲も変わらない(`diff` 差分なし)。

**採らなかった案**: 「ベースがキーの音階外のとき、2 秒層のコード切り替えコスト(`switch`)を割り引く」。割引率 0.6 / 0.3 / 0 で confirmed の majmin が .823 → .821 / .819 / .813、tetrads .634 → .633 / .632 / .624、0 ではコード数 36.6 → 45.8/分に増えた。この区間の aug は事前値だけで出るので、割引の効果もなかった。
